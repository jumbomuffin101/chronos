# Partial typed operation observations

Status: opt-in in-memory prerequisites, not a complete replay stream, journal schema, durable authorization or recovery implementation. The dispatcher and its diagnostic index remain as described in [the preceding design](phase7c2a3b4-unified-mutation-design.md). This milestone adds typed observations only for direct owner submit, cancel and conditional private-report dequeue. They do not cover all owner mutations, so their indices may have gaps and must not be treated as authoritative operation positions or future LSNs.

## Proposed domain and excluded state

Matching/book FIFO, remaining orders, risk policy/positions, ownership and exchange/matching/feed counters are continuation state. Session creation/closure, kill and policy updates and private report queues can change later acceptance; they require ordered records or a verified checkpoint and suffix. Private report dequeue affects queue capacity and must be replayed or reconciled before admission. Public subscription queues and gap markers can be reset only by ending prior sessions and requiring fresh snapshots; feed sequence itself remains authoritative. TCP sockets, buffers and peer delivery are not recoverable; a completed write is not an application acknowledgment. No new connection is authenticated to a retained session.

Owner construction, bind/finish and exclusive/shared allocator registration are outside these observations. A future boundary must establish exchange identity and epoch, capacities and initial state, acquire exclusive publication authority, verify exact allocator high-water against all retained historical IDs, and gate admission while reconciling other allocator users. Process-local registration does not provide cross-process exclusion or crash durability. Isolated exchange allocators are separate. Disconnect and gateway lifecycle must be ordered or explicitly modeled at a verified boundary.

## Implemented typed inputs and outcomes

* `submit_recorded` and `cancel_recorded` invoke the existing direct exchange method once through the owner dispatcher. `CommandRecord` contains the existing exact 52-byte canonical command, the owner-local diagnostic index and the actual `Result`. Accepted means the existing direct transaction returned accepted; other enumerated results represent business rejection. It does not include the reserved ID, counters, fills, reports, risk effects or book state. No record is returned if preparation/allocation/owner checks throw; these failures are not business rejections. These methods are opt-in and are not used by the gateway or prepared authorization path.
* `consume_expected_report(session, expected_sequence)` checks the current private queue front. Zero session/sequence is `Invalid`; no front is `Empty`; a different front is `Mismatch`; only an exact match is `Consumed`. A mismatch leaves the front and capacity unchanged. The returned `DequeueRecord` has recipient, expected and observed sequence, status and diagnostic index. Each normally completed call counts in the diagnostic index, including invalid/empty/mismatch. A repeated request cannot consume a later report because its sequence differs. Unknown session and empty queue both report `Empty` under this narrow API. Existing blind `pop` remains available, and the gateway still uses it, so this API does not establish complete coverage or transport delivery.

The private report `sequence` is allocated from the exchange event counter and is unique within an exchange lifetime until checked exhaustion; recipient plus sequence identifies the expected front within that exchange. A process restart or different exchange can repeat the pair. A future replay envelope must bind it to authenticated exchange identity and epoch and strictly preserve report sequence, identity and queue contents. This is consumption from in-memory exchange state, not a claim that a TCP peer or application received the report.

The existing index is a completed-call diagnostic: it also counts calls for which no typed record is produced, no-ops and business rejections, so gaps and unrelated activity are expected. Callback abort and internal exceptions do not advance it. It is neither a record-stream index nor durable LSN. No restricted owner mode prevents unrecorded operations. The result types represent actual completed outcomes; preparation failure, exception and transaction abort are deliberately propagated through existing APIs and are not fabricated as serialized records. A future schema needs explicit distinct classes and authoritative admission rules for those paths.

## Experimental binary encodings

All integers use network byte order. Encoders allocate no heap and decoders require the exact byte count. Records are local experimental formats, not stable journal envelopes. Reserved bytes and unknown version/kind/status are rejected; no trailing bytes or native struct layout is accepted.

`DequeueRecord` is 40 bytes: u16 version 1, u8 kind 1, u8 status (1 consumed, 2 empty, 3 mismatch, 4 invalid), four zero reserved bytes, u64 diagnostic index, u64 session, u64 expected report sequence and u64 observed front sequence. Index must be nonzero. Consumed requires nonzero session/expected and observed equal expected; empty requires nonzero session/expected and zero observed; mismatch requires nonzero unequal expected and observed; invalid requires zero session or expected and zero observed. An invalid record cannot be encoded or decoded.

`CommandRecord` is 68 bytes: u16 version 1, u8 kind 2, u8 status (1 accepted, 2 business rejection), u16 result code, two zero reserved bytes, u64 diagnostic index, followed by exactly the existing 52-byte canonical command. The explicit result-code table fixes codes 1–17 for the current `Result` variants; status must agree with result and the embedded canonical input must pass its own strict decoder. Unknown result values, zero index and unsupported version/kind are rejected. Command fields are encoded by the existing fixed-width canonical codec, including exact signed price bits. Neither format includes an exchange identity, ordering epoch, checksum or durable record framing.

## Remaining operation variants and verification

Session open/close, full risk limits and allowed-symbol list, kill, subscribe/unsubscribe, public dequeue and subscriber gap transitions have no implemented typed observations. Nor do prepared submit/cancel outcomes, report routing, counter deltas, allocation high-water or installed-summary effects. A future schema must encode bounded fields and real outcomes for each, establish whether rejected/no-op operations are admitted, and route or restrict all bypasses. It must distinguish pre-admission validation, abort, internal exception and allocation failure without manufacturing results or weakening exception safety. Adding format fields before the owner and allocator boundary is proven would not establish replay.

Exact continuation-state words can compare book/FIFO, actual IDs, ownership, policy, positions, queues, exchange and matching counters, feed state, capacities and allocator high-water in compatible contexts. The words are a bounded diagnostic, not a stable wire format; the owner diagnostic index is separate. Future end-to-end replay must compare full state after each operation against an independent expected execution and reconcile queue consumption and allocator authority. No digest is used as proof of equality.
