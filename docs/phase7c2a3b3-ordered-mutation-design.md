# Ordered recovery-state mutations: design and current boundary

Status: design plus narrow opt-in administrative preparation. **There is no implemented authoritative operation index, durable journal, replay of these operations, or live recovery.** Existing gateway behavior is unchanged. The comprehensive [prior mutation inventory](phase7c2a3b2-recovery-state-inventory.md) remains applicable; the table below adds proposed admission and ordering rules.

## Proposed single-owner timeline

The existing gateway owner thread must dispatch every continuation-affecting operation through one owner-controlled boundary, including I/O-driven lifecycle and queue consumption. Other threads enqueue bounded requests and never mutate Exchange. Socket receive order across independent clients is not intrinsically deterministic: the owner records its actual chosen dispatch order. A future operation identity is `(exchange identity, epoch, operation index)`, distinct from a storage LSN. Establish identity/epoch before enabling replay. Index zero denotes the initial boundary; increment once after all preparation and authorization of a terminal accepted operation or authorized business rejection, immediately before the nonthrowing install/publication boundary. Check exhaustion before admission; never wrap or reuse an index within an epoch. Preparation failure, cancellation before authorization, internal exception, or inability to reserve required resources does not consume an index or expose state. A business rejection is recorded as such when the ordering policy admits it; current Exchange business rejection leaves exchange state unchanged. Internal failures are not silently relabeled as business rejections.

The index is volatile unless a separately authorized storage protocol establishes otherwise. A durable LSN, if later designed, must bind the same operation to its own storage identity and commitment/ack rules; assigning an in-memory index does not authorize or imply durability. Ordering and state installation need a reviewed atomic boundary. If a recorder can fail after an index is allocated, the future owner must fail closed or use a staged index that is not published until all required resources and authorization are ready. No index is introduced by this patch because multiple live mutations still bypass an integrated dispatcher and assigning only some operations would create misleading sequence gaps.

## Operation inventory and proposed treatment

Each entry is executed by the live owner unless stated. Admission includes owner lifecycle and resource checks; any internal exception is an internal failure. `Replay` means record the operation in owner order or capture it in a verified checkpoint plus subsequent ordered suffix, not that replay is implemented. `Reset` requires a deliberate fresh-session boundary. The existing normal gateway does not emit these records.

| Operation / before → after | Admission and rejection | Continuation and recovery rule |
| --- | --- | --- |
| Open session: absent → account with default limits, queues and empty ownership | Nonzero unique ID and capacity; failure leaves state unchanged. Current gateway follows open with a separate risk configuration and may close on failure. | Affects identity, capacity and future risk/report routing. Replay ordered open and risk operations, or capture in checkpoint. No authenticated reuse. |
| Close/disconnect: subscriptions cleared; account erased only when no reports and no order history | Missing ID is a no-op; transport loss can happen independently of commands. | Retained ownership, position and report obligations affect continuation. Replay close or explicitly checkpoint; new socket is a new session. Do not assume retained session identity authenticates a new connection. |
| Configure risk: previous limits → new validated limits | Existing session, valid bounds, no open orders, positions within new limit. Failure preserves state; allocation may throw. | Replay exact complete policy including ordered symbol list, not just scalar summary; affects future admission. |
| Kill switch: old → requested flag | Existing session required; missing session returns false without mutation. | Replay in order; resting orders remain executable and cancellation policy remains current implementation's. |
| Submit / cancel: live state → staged candidate or unchanged rejection | Owner, validation, risk, ownership, capacity, counters and allocator govern outcome. Abort/exception destroys candidate. | Replay input plus accepted/rejected decision. Verify trade, reports, positions, open orders, IDs and counters. Authorized business rejection may need an ordered record despite no state change. |
| Fill, position, exposure and ownership changes | Internal effects of accepted submit/cancel, not separately admitted operations. | Replay as part of parent command; no invented reservation ledger. Book, FIFO, touched ownership, positions and derived exposure must agree. |
| Matching/exchange counters, book revision, feed sequence, order-ID allocation | Changed within accepted transactions, subject to checked exhaustion and allocator reservation. | Replay/verify exact values; allocator high-water and exclusive ownership require process-wide startup reconciliation. |
| Subscribe / unsubscribe: subscription generation and snapshot queue inserted, replaced or removed | Existing session, bounded subscriptions and generation; invalid requests unchanged. | For exact live-delivery replay, order operations and retain generation/queues. Alternatively reset all old public subscriptions under explicit fresh-session/resnapshot policy; never claim continuity. |
| Feed publication and gap: feed counter and subscriber queue/gap state change | Derived within parent matching transaction; full queue transitions to gap. | Feed sequence is authoritative; gap/queue may reset only if old subscriptions end and clients resubscribe. Parent public events alone do not reproduce subscriber-specific state. |
| Public dequeue: matching front/generation removed or gap marked sent | Only a matching in-flight event affects state; stale pop is a no-op. Current gateway calls it after socket write completion. | May reset with old public subscriptions; otherwise order it to reproduce delivery state. Kernel writes are not application acknowledgments. |
| Private dequeue: front report removed | Existing session with queued report; otherwise no-op. Gateway pops after bytes are written. | Queue occupancy changes later admission. Replay exact dequeue and retention or reconcile obligations and gate admission; silently resetting can change acceptance and lose private reports. |
| Gateway shutdown, disconnect and pending controls | Socket and owner event-loop state; controls may be rejected before start, completed, or fail on shutdown. | Socket state is reset, but order lifecycle and private obligations remain authoritative. Define an ordered shutdown/admission cutoff and uncertain outcomes; no durable acknowledgment exists. |
| Ownership registry / owner bind and finish | Registration, active context and process allocator are distinct lifecycle controls. | Startup must acquire exclusive publication authority, verify identities and allocator high-water before admission. Record/configure boundary externally; never introduce another state owner. |

Current bypasses include `LiveExchangeOwner::open_session`, `close_session`, `configure_risk`, `set_killed`, `subscribe`, `unsubscribe`, `market_pop`, `pop`, direct `submit`/`cancel`, and owner bind/finish. Gateway invokes these directly for accepted connections, admin controls, subscriptions, completed socket writes and disconnect cleanup. The exclusive gateway uses prepared submit/cancel, whereas the shared mode follows its existing path. Internal position, ownership, counter and gap changes are nested effects, not separate API calls. The test-only allocator seed is not a production operation. All remain serialized by owner context but not by an explicit recorded operation index.

## Administrative schemas and recovery classifications

Future bounded, versioned operation payloads must include owner operation identity, kind, explicit outcome and enough inputs to reproduce it. Proposed variants: `Open(session)`; `Close(session, reason)`; `SetRisk(session, all scalar limits, bounded allowed-symbol list)`; `SetKill(session, bool)`; `Subscribe/Unsubscribe(session, symbol)`; `PrivatePop(session, expected report sequence)`; and `PublicPop(session, symbol, generation, kind, sequence)`. Strictly validate sizes, enum values, duplicate IDs and expected-front identities. Current `pop(session)` does not itself validate a supplied expected report sequence, so replay-safe conditional dequeue is not implemented. Gap transitions are deterministic derived output of parent events and queue state; a separate record is necessary only if the future boundary chooses not to reproduce that state.

**Replay exactly:** sessions retaining orders/obligations, admin risk/kill changes, accepted commands and their outcomes, ownership and allocator/counter effects. **Reset explicitly:** TCP connections, kernel buffers, old public subscriptions and gaps, only under a new epoch/session policy with fresh snapshots. **Reconcile or gate admission:** private queues, report consumption and identity association, because queue capacity changes later decisions. Secure reattachment and application acknowledgments are outside this milestone. Never deliver retained reports to a newly connected client solely because an integer identity matches.

## Implemented preparation and verification

`LiveExchangeOwner::with_prepared_open_session` and `with_prepared_risk_update` are synchronous opt-in scoped APIs for exclusive owners. They privately clone the exchange state, invoke existing validation/mutation code, and expose only the existing accepted/rejected result to a callback. False or exception destroys the candidate; true installs an accepted candidate with the existing nonthrowing unique-pointer swap. Risk configuration currently clones again internally. Neither operation reserves an order ID or emits reports or market events. `InvalidOrder` represents any boolean administrative rejection and is not a detailed reason. No handle or mutable candidate escapes. The normal gateway does not call these functions, and no callback grants durability. The owner is frozen against reentrant mutation throughout. Other administrative operations remain unprepared.

The existing `exact_continuation_state(max_words)` provides bounded diagnostic exact words covering real order IDs, owners/history, positions and full limits, report and subscriber queues, exchange/matching counters, feed sequence, book levels/FIFO, revision, capacities and allocator high-water. It is not a stable canonical codec or independently authenticated recovery proof. Open exposure is derivable from the exact books and ownership and must be checked with overflow-safe arithmetic; it is not a separate ledger. Normalized Phase 7B words relabel IDs and cannot establish actual allocator identity. Compare exact words when identity contexts match; no digest is specified or claimed as proof. Capturing a full vector per command costs O(full state) memory/time and is not adopted as the per-operation design.

Before implementing a durable writer, integrate every bypass in one owner boundary, specify full schemas and bounded resource/error handling, reconcile private obligations and global allocator ownership, establish snapshot/journal identity and fault-injected persistent commit ordering, then validate recovery without publishing partial candidates. No crash durability, secure reconnect or exactly-once client delivery is provided.
