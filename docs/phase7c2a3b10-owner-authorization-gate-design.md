# Isolated owner authorization gate

The authorization harness models a separate owner and is not itself a gate on the recorder. An explicitly in-memory opt-in constructor on `RestrictedReplay` guards the actual `apply` installation and record-slot publication. The ordinary constructor selects the existing direct path. No mode transition is exposed. Neither mode represents storage durability.

The gate prepares a private clone, canonical state and preallocated record, then binds a bounded request to owner identity, fixed configuration and capacity, operation sequence, previous chained request digest, command, outcome, and length-delimited exact legacy and canonical records. SHA-256 covers the entire request. A closed in-memory authority owned by the recorder returns its own digest and length; caller-supplied tokens cannot confer authority. Test-only controls simulate explicit precommit refusal and ambiguous or mismatched decisions. Refusal discards the candidate; ambiguity or mismatch fail-stops admission and withholds outcomes. Verified authorization permits pointer swaps and one sequence increment; the request buffer remains alive through publication. The chained digest is an in-memory prefix identity, not a journal offset or trusted terminal anchor.

The owner rejects wrong-thread calls and admission in preparing, awaiting, authorized, and failed-stop states. The closed synchronous authority has no callback and therefore cannot reenter the owner or be interrupted by an owner-thread shutdown request; this is not an asynchronous shutdown protocol. A future asynchronous authority needs a separately reviewed lifetime, cancellation and fail-stop protocol; destruction after a possibly committed external decision must never be described as rollback. SHA-256 binds bytes but does not authenticate the authority, establish a durable terminal boundary, or prove stream completeness. The in-memory decision implementation does not claim any of those properties.

The private allocator remains confined to the isolated candidate. Real storage, manifest trust, crash recovery, allocator lease coordination, session recovery and live gateway publication remain outside this design and require separate implementation and verification.

The initial prefix is 32 zero bytes. Each admitted operation, including a business rejection or no-op, advances the sequence and replaces the prefix with the SHA-256 of the exact request, which itself contains the preceding prefix. Aborted preparation and explicit refusal do neither. A separate test independently reconstructs requests from the installed legacy and canonical records, the inputs and actual outcome, and compares each computed prefix. The test-only seam can replay an earlier decision against a later operation; that attempt fail-stops without installation. A hash chain is not a trusted terminal or proof of an authenticated history.

The authority is a private closed object, and `apply` does not accept caller-provided tokens or callbacks. There is no API for a different authority instance, delayed responses, cancellation of a pending decision, or asynchronous stop; such cases are not exercised by the synchronous implementation. Wrong-thread calls are rejected. Within `apply`, the preparation guard is set before candidate cloning and allocations; a nested owner mutation is rejected. On a checked authorization, the prepared request remains alive as state and preallocated record pointers are swapped and the bounded count advances, using nonthrowing operations without callbacks or I/O. The old state and request are destroyed after publication. A simulated ambiguity fail-stops this object, but a newly constructed object has no persisted failure state. The latter is a hard blocker for external durable decisions.

The synchronous in-memory authority is not a storage-authority abstraction. Do not treat this milestone as ready for storage integration.
