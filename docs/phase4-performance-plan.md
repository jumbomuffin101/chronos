# Phase 4 performance plan

## Current transaction cost

After input validation, every valid `submit` clones the entire book, including market orders with no liquidity and commands later rejected due to overflow or exhausted event/trade counters. `cancel_resting` and `modify_resting` also clone before checking whether the requested order or modification succeeds, unless the command counter is already exhausted. Invalid submissions and duplicate IDs are rejected before cloning. Each clone allocates new map, list and index nodes and copies the resting orders in FIFO order. For `N` orders and `P` price levels, expected cloning work is `O(N log P)` with the current repeated map insertion and expected hash lookup costs; hash collision worst cases can be worse. It requires `O(N + P)` extra space, in addition to output storage `O(F)` for `F` fills. Both original and working books coexist until the commit finishes. Matching and level removal add up to `O(F log P)`; exact cost depends on whether levels disappear.

Copying touches orders unrelated to the command, adds allocations, and increases expected per-command work and peak memory as the book grows. This is a complexity analysis, not a measured latency claim. Full-book copying provides a simple isolation boundary: allocation, validation, counter exhaustion or staged fill failure discards the clone and output. The final pointer swap and counter assignment are nonthrowing, the result is nothrow movable, and the replaced book is nothrow destructible. An allocation failure when constructing even a rejection report can still throw; no book state or accepted counters change.

## Candidate designs to evaluate

1. **Prevalidated execution plan.** Read the affected price levels into a plan; check all quantities, counters, residual-level capacity and selection identities; allocate all reports, trades and any nodes needed by a remainder before applying changes. Commit must use only operations proven not to allocate or throw. Planning and allocation failures then leave the book unchanged, but the design must handle iterator lifetime, ID reuse, output ownership and staged insertion carefully. A plan that merely reserves vectors without reserving map/list/index nodes is not sufficient for atomicity. Serialized mutation is required between planning and commit; a revision token can detect stale plans.
2. **Bounded undo journal.** Record enough prior state, FIFO positions, index locations, aggregates and counters to reverse every mutation, then apply changes in place. Journal capacity must be obtained before mutation and bounded commands need a defined rejection path when the bound is exceeded. Rollback itself must not allocate or throw, including when restoring a removed node or price level; detached nodes or preallocated resources may be necessary. This can reduce copying for small affected sets, but complicates ownership and failure analysis.

Both options must preserve event ordering, checked counters and overflow behavior, stale-selection protection, ID reuse rules and all-or-nothing outcomes. A third option is persistent/copy-on-write structures, which can share unaffected state but introduce ownership and memory-management complexity. None is approved as an implementation yet. Future durable logging or publication introduces a separate commit boundary that neither an in-memory plan nor a journal solves by itself.

## Benchmark-first sequence

1. Establish a reproducible Release baseline on a documented machine and toolchain. Use fixed seeds, warmups, repeated independent runs and explicit book setup; validate outcomes against a reference implementation outside timed regions.
2. Vary total resting orders, levels, orders per level and bid/ask distribution. Measure noncrossing limits, empty-book markets, one-fill and many-fill commands, same-level and multi-level sweeps, partial/full fills, cancellations, same-price modifications, price changes, duplicate and overflow rejection. Include rejected maintenance commands because they currently clone.
3. Record per-command latency distributions and throughput, allocation counts/bytes and peak resident memory. Separate setup, snapshot queries, matching, clone and output construction where feasible. Report workload and sample counts; avoid inferring production latency or publishing unsupported numbers.
4. Profile representative cases to identify whether clone allocation, indexing, price maps, reports or other costs dominate. Use system-level profiling with stable CPU scheduling and document any virtualization or filesystem effects.
5. Prototype one alternative behind the same observable contract. Compare against the baseline and deterministic reference, inject allocation failures at every staging/commit boundary, and verify counters, FIFO, stale selection and rollback under multi-fill failures before accepting a speedup. Retain the clone-based implementation as a correctness oracle until the new design is independently validated.
