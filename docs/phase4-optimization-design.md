# Phase 4B transaction design

## Baseline and alternatives

The Phase 4A engine clones the whole book for each valid submission and each maintenance operation, then generates output and mutates the clone before swapping it into place. This is a useful correctness oracle but copies unrelated orders and allocates proportional to book size. A bounded undo journal could mutate in place, but must retain extracted nodes and preallocate all rollback storage; proving reversal of every map/list/index mutation without allocation is complex.

The proposed alternative is a prevalidated execution plan. The engine privately traverses resting orders in price-time order without exposing iterators, stages trades and reports, and checks all counters and revision capacity before mutating the book. It then inserts any limit remainder using the book's existing strong exception guarantee. This insertion is the first mutation; all operations after its success must be nonthrowing. A private book primitive consumes the predetermined best heads without allocating, followed by nonthrowing counter assignment and outcome move. The book is engine-owned and calls are serialized, so there is no mutation or callback between planning and commit. Public selections and their revision checks remain intact. The original clone path remains selectable as a reference.

## Commit proof obligations

Before any mutation, validate the request, build all trade/report vectors, check command, trade, event and book-revision headroom, and derive the final remainder. If insertion is needed, the existing `add` either succeeds or rolls back its list and level on allocation/index failure; its aggregate check rejects overflow. Only after it succeeds may best-head removals or reductions occur. The private fill primitive must use only existing nodes, nonthrowing integer arithmetic, nonthrowing identifier/hash/comparison and destruction, and container erasure; it must not allocate, call external code, or expose its iterators. A staged order is on the incoming side, so it cannot change the opposing best heads. Counts and quantities are computed from the same serially held book. After the first mutation, no failure result or exception may be introduced. Revision exhaustion is checked in baseline order so error classification remains the same. The outcome vectors and counters are fully formed before commit; `Outcome` move and counter assignment are nonthrowing.

Maintenance cancel and modify already provide strong failure guarantees at the book boundary; the engine can call them directly and advance counters only on success. Price changes first allocate their destination before removing the source. No concurrency or reentrant user callbacks are allowed. Allocation failure during planning or staging propagates and leaves the book and counters unchanged. Durable publication remains outside this in-memory transaction.

## Verification requirements

Use deterministic differential tests against the clone mode, including all output fields, event order, counters, depth and FIFO order. Inject allocation failures at every allocation reached in plan construction, output staging and remainder insertion; verify unchanged state and counters on failure. Test counter and aggregate exhaustion after planned fills, invalid/stale selections, maintenance and ID reuse. Benchmark both modes using the same harness, workload and reset procedure, and report tail-sample and WSL limitations. This is a design and proof obligation, not a claim of measured speedup.

## Implemented boundary

The planned path traverses only the opposing price-time prefix needed for the command. Its staged `Trade` vector doubles as the fill-quantity plan; all event reports are also built before mutation. It checks revision headroom in the clone path's logical order, including the distinct remainder-insertion failure case, and checks the destination aggregate before staging a remainder. The remainder's ordinary `add` may allocate and is the last potentially throwing operation. It is inserted on the incoming side, so it cannot alter the selected opposing prefix. The plan retains values, not list, map, or hash iterators: a remainder insertion can rehash the ID index, and each fill performs a fresh index lookup. Once insertion succeeds (or immediately before the first fill when no remainder exists), `consume_best` is called for each staged quantity. It uses existing nodes, integral subtraction, fixed nonthrowing identifier hashing and comparison, iterator erasure and nonthrowing destructors; it is `noexcept` and never allocates. The last steps are checked-at-compile-time nonthrowing counter assignment and `Outcome` move. The book and traversal are private to the serialized engine, and no external code or callbacks run during this boundary. A broken internal invariant in the `noexcept` primitive would terminate rather than roll back; correctness therefore depends on the documented preconditions and invariant tests.

With `F` fills and `P` price levels, planning and commit visit the affected prefix and use expected `O(F)` hash work plus `O(log P)` lookup/insertion for a limit remainder; hash-table rehashing and hash collisions can cost more, and vectors require `O(F)` space. Successful cancellation is expected `O(1)` aside from empty-level removal; modification may need `O(log P)` destination work. The clone reference continues to copy `O(N + P)` storage and visit the whole book. No timing is implied by these bounds. The retained reference is selected with `TransactionMode::CloneReference`; planned is the default.

The allocation-failure tests iterate failure positions through multi-fill output staging and remainder insertion into both new and existing price levels. The existing-level test additionally returns successfully while the next allocation is configured to fail, verifying that the exercised path completes without another scalar `new`; this does not instrument every possible allocation mechanism. The 1,000-command fixed-seed differential test compares all trade/report fields, counters, depth and per-level FIFO state after each submission or maintenance operation, and a separate boundary test compares counter and aggregate overflow behavior. These are evidence, not a formal proof or a test of concurrent/reentrant usage, which is unsupported.

Final-review regressions also compare remainder staging and multi-level fills across a range of index sizes, and exercise a no-remainder full-fill commit while the next scalar allocation is configured to fail. Index rehash thresholds are implementation-specific; the test covers many sizes rather than asserting a particular library's bucket policy.
