# Live owner mutation boundary

This change introduces a non-reentrant in-memory boundary inside `LiveExchangeOwner`. It is not a durable journal, canonical record, recovery system or globally authoritative mutation sequence. The existing gateway owner thread remains the only mutator of its encapsulated live exchange; shared and exclusive gateway modes retain their existing exchange logic and protocol. Isolated `Exchange` instances and other live exchange owners remain independent.

## Coverage and owner call-site inventory

Every listed public owner mutation below invokes `dispatch_mutation` once. The boundary checks active owner context, rejects reentry, prechecks counter exhaustion and invokes the existing exchange operation. A normal return advances a volatile diagnostic index after the operation completes; exceptions leave the index unchanged. Accepted/rejected result values and `PreparedScopeResult::installed` remain the caller's way to distinguish outcomes. No attempt is made to create a journal record.

| Owner entry points | Exchange mutations and nested effects | Recovery implications |
| --- | --- | --- |
| `open_session`, `configure_risk`, `set_killed`, `close_session` | Session table, limits, kill flag, subscriptions; close retains sessions with any order history or pending reports. | Session identity, risk and retained ownership must be reconstructed in order. Gateway opens then separately configures risk; both calls are visible to this boundary. |
| `submit`, `cancel`, prepared non-durable variants, summary variants, `with_prepared_submit/cancel` | Candidate matching, FIFO and quantities; ownership, positions, risk exposure, order ID reservation, reports, audit, feed counters, queues and gaps. | Nested effects belong to the parent operation; report and public events are still published only under existing gateway rules after installation. |
| `with_prepared_open_session`, `with_prepared_risk_update`, `with_prepared_close_session` | Private candidates using existing exchange logic; closure clears subscriptions without cancelling resting orders or losing retained reports. | The callback sees only an outcome and can abort; the candidate cannot escape. A close for an absent session returns `InvalidOrder` in this prepared API; direct close is a no-op. |
| `subscribe`, `unsubscribe`, `market_pop` | Subscription generation, snapshot/event queues, gap state, conditional front consumption. | Feed sequence and source market events are authoritative. Old subscriber state may reset only with explicit new-session/resnapshot policy. |
| `pop` | Removes one private front report, if present. Gateway calls after its socket output is written. | Queue capacity affects future admissions. Reproduce/reconcile the exact recipient and front report before admitting recovered commands; completed TCP write is not a client acknowledgment. |

The gateway call sites include accept (`open_session`, risk setup and failure close), dispatch (submit/cancel, subscribe/unsubscribe), control queue (risk/kill), write completion (private/public pop), and dead-session cleanup (`close_session`). Socket reads, writes, poll activity, ingress ordering and gateway shutdown state are transport operations outside this counter. Generated reports, book changes, gap transitions and ID reservation are nested inside their owning submit/cancel or subscription call, not separate index entries. `bind` and `finish` are lifecycle transitions outside the boundary; `finish` is prohibited during dispatch and remains available after index exhaustion. Test-only allocator and diagnostic seed seams bypass the index. Direct public `Exchange` instances, isolated simulation/replay exchanges, other owner instances, and process-global allocation activity caused by them are outside this owner's counter. `with_frozen_state` is an exclusion callback, not a mutation dispatcher; it forbids owner mutation while active.

## Diagnostic ordering and failure semantics

The counter starts at zero for each owner and increments once for every normally completed dispatched call, including rejected commands, absent-session operations and conditional dequeue no-ops. Thus it is a **completed-call index**, not a count of committed mutations; outcome/installed flags must be considered separately. A scoped prepared operation increments only if its authorization callback returned true, including an authorized business rejection. False, a thrown callback, an allocation error, failed owner/exclusive checks or other exception leaves it unchanged. Summary calls have immediate non-durable authorization and count completed rejections. The index is checked before the operation and `UINT64_MAX` fails closed with `std::overflow_error`, including for calls that would be no-ops. It does not wrap. `finish` can still stop the owner.

The dispatch guard blocks nested entry and resets on every exception. Prepared callbacks run under the existing frozen scope; no install handle or mutable candidate escapes. All returned values used by the boundary must be nothrow-movable so a committed state cannot be followed by a throwing return before index advancement. The exchange's candidate install is the existing nonthrowing pointer swap and optional nonthrowing allocator reservation commit. The index increment is nonthrowing but occurs after installation; it is neither persisted nor atomically bound to external publication. No journal LSN, epoch, input record, recipient/report identity, failure reason, authorization record or replay API is emitted. It is deliberately **not** an authoritative recovery timeline, even though the listed owner methods are covered.

The test-only diagnostic seed can force exhaustion and is not exposed by production targets. Other live allocator users in shared mode and process restart can produce state changes or reset this index without an entry. A future durable boundary must identify an exchange and epoch, constrain all allocation and lifecycle entry points, record complete commands and outcomes including report-front identity, define authoritative business rejection admission, and bind state, index, storage authorization and publication in one failure-atomic protocol. Do not infer durability from callback acceptance.

## Recovery domains and closure

Matching continuation requires exact books, level order/FIFO, remaining quantities, matching counters and revision. Risk and ownership require complete sessions, historical request/order identities, limits, kill flags, positions and derivable open exposure. Private report obligations and occupancy can change future command admission and must be replayed or reconciled under closed admission. Public subscription queues and gap markers may be discarded only after terminating old sessions and requiring fresh subscriptions/snapshots. Gateway sockets, write buffers and thread scheduling are not recovered. Session identity is currently local and unauthenticated: never attach retained private obligations to a new connection merely because an integer matches.

Prepared close clones the private state and uses the actual `close_session`: active subscriptions are cleared; a session with an open or historical order or queued report remains, preserving resting liquidity and risk/ownership. An empty session with no history or reports is erased. No trade or counterparty fill is generated by closure. Aborted/throwing preparation leaves exact live state unchanged. A disconnect after a socket write can leave delivery uncertain; there is no application acknowledgment or exactly-once claim.

The bounded `exact_continuation_state` vector verifies exact IDs, ownership, FIFO, positions, policy, queues, counters, feed and allocator high-water for compatible exclusive contexts. It does not include this owner-side diagnostic index, which must be checked separately. It is not a versioned canonical codec, digest proof or live restore interface. Full reconstruction and verification, authoritative ordered representations, allocator reconciliation, durable storage failure behavior and crash-consistent publication remain separate work.
