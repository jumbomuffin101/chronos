# Canonical-native isolated recording

This is an in-memory change to the existing restricted isolated replay domain. It is not a durable journal, live gateway recovery, authenticated reconnect or exactly-once delivery mechanism. The supported operations and fixed initial configuration remain those in [the restricted replay design](phase7c2a3b6-restricted-replay-design.md). The [canonical schema and envelope](phase7c2a3b7-canonical-replay-state-design.md) are unchanged; its description of the old recording/sealing lifecycle is historical.

## Original and current preparation

Previously each `RestrictedReplay::apply` rebuilt an isolated exchange by executing and checking the entire previous history, executed the new operation, and stored diagnostic words. `CanonicalReplayEnvelope::seal` replayed the history again to manufacture canonical snapshots. Those snapshots were not retained directly from the candidate installed by the original call.

The current owner validates its creating context, input shape and 128-operation capacity, then makes a private clone of its **current** isolated Exchange. The private clone preserves the current private allocator high-water and copies sessions, risk, ownership, books, counters, reports, audit and feed state using existing clone logic. It rejects a live exchange or active public-capture sink. The owner executes only the new operation on that candidate through the existing Exchange implementation, captures diagnostic continuation words and, for an operation to be committed, encodes canonical bytes directly from that same candidate. It encodes the legacy bounded operation/outcome record and allocates a private `InstalledRecord` holding both byte vectors before installation. The canonical state includes the actual configuration fields and private allocator high-water; the final envelope additionally binds the fixed configuration identity tag.

The owner has a fixed array of 128 initially empty `unique_ptr` record slots. After every potentially throwing operation succeeds, it swaps in the candidate state, swaps the prebuilt record into the checked empty slot, and increments the count. Both pointer swaps and the count increment are nonthrowing; no allocation, callback, external publication or observer occurs between them. A test-only execution counter verifies that `apply` executes only the requested operation, `seal` executes none, and the offline verifier executes the history. The previous state is destroyed after publication through a nonthrowing Exchange destructor. One owner context and no escaping candidate or prepared handle prevent a stale candidate from overwriting newer state or being installed twice.

Invalid input, owner-context failure, capacity exhaustion, allocation failure, canonical size-limit failure or exception before the swap leaves the installed state, records and count unchanged. `apply(op, false)` deliberately discards the private candidate and does not advance the sequence. Completed business rejections and no-ops are still recorded once, even when canonical state is unchanged; result values come from the actual Exchange operation. Sequence numbers remain contiguous from one and are not durable LSNs. Capacity is checked before preparing a candidate. The test-only canonical byte limit exercises record-size failure; production uses the fixed 65,536-byte canonical limit and 8,192 diagnostic-word limit.

## Sealing and independent verification

`CanonicalReplayEnvelope::seal` validates owner context, constructs the fixed initial-state hash, decodes each installed legacy record only to obtain and validate its sequence/input/outcome, and copies the **originally captured canonical bytes** from the corresponding installed slot into the envelope. It does not execute the operations or reconstruct their expected states. It compares the last captured canonical state with the owner's current canonical state; for an empty stream it compares the initial state. Sealing can allocate and fail, but it is read-only and does not change the owner.

The existing envelope includes caller-supplied nonzero context identity, fixed configuration and initial-state hashes, private allocator scope, initial and terminal sequences, count, exact terminal offset and SHA-256 over the complete stream with its digest field zeroed. An independently trusted external anchor must bind identity, terminal sequence and digest to resist substitution or undetected truncation. A self-supplied anchor is not authentication.

`CanonicalReplayEnvelope::verify` remains an offline independent execution: it validates the bounded envelope, creates a fresh isolated Exchange, executes each encoded operation, compares the actual result and newly encoded canonical bytes against the **originally recorded** bytes, and rejects divergence. It shares the production matching and risk implementation with recording and is not an independent matching-engine oracle. `RestrictedReplay::verify` still provides the separate diagnostic-word comparison. Neither verifier can publish its candidate to the gateway.

## Resource and safety boundaries

All operations are owner-thread-only. The domain has no subscription, kill-switch, live gateway or mutable Exchange accessor. Private order IDs can repeat in other isolated contexts and never become live IDs through this API. The existing global allocator is not reserved or changed. Record and state bounds, exact expected-report identity and session-close behavior are unchanged. Records store both legacy diagnostic and canonical state, so memory remains bounded but full-state snapshot amplification persists. `records()` and `recorded_canonical()` return copies; callers cannot mutate installed slots.

Native recording eliminates repeated execution of the entire history on the normal path, but each operation still clones current state, executes existing Exchange logic (which can itself clone), and encodes full diagnostic and canonical states. With growing state this can still produce O(n²) total copying/storage over n operations. Sealing is linear in the stored record/byte volume plus hashing, rather than replaying matching; independent verification still executes every operation. This is a correctness prototype, not a latency or durability claim.

Future work must define persistent authorization and a stable canonical-native record format, authenticated stream identity and terminal boundary, storage sync/fail-stop semantics, allocator reconciliation and publication gating, client identity and private-report recovery, and crash testing. No `fsync`, manifest, live recovery or exactly-once delivery is implemented.
