# Phase 3 matching design

Historical design: Phase 4B introduces a planned transaction mode while retaining the cloned-book implementation as a reference. See [Phase 4B design](phase4-optimization-design.md) for the current transaction boundary.

## Boundary and algorithm

`MatchingEngine` owns one book for one symbol and serializes calls. `submit(Request)` validates side, type, symbol, price, quantity and active ID before accepting a command. A buy crosses asks at or below its limit; a sell crosses bids at or above its limit. A market order ignores limit prices. Each execution consumes the FIFO head at the best opposing price for the smaller remaining quantity and executes at the resting price. An unfilled limit remainder rests; an unfilled market remainder is cancelled. There is no self-trade prevention, risk, transport, persistence, or concurrency.

The book provides `best_resting(side)` and `apply_fill(selection, quantity)`. A selection contains a copied order, a book identity and revision. Any successful book mutation invalidates all prior selections, including after ID reuse; rejected operations do not. A selection also cannot be used on another book or its clone. Revision overflow rejects mutations rather than wrapping. The selection exposes no internal iterator, and the book owns all nodes. Only the current best FIFO head can be selected; invalid or stale fills leave the book unchanged. Partial fills retain position and full fills remove the order, index entry and empty level.

## Atomic command boundary

After validation, the engine clones the book, uses local counters, and constructs output vectors while applying matches to the clone. A successful complete command swaps the owned book pointer and commits counters; rejected commands return no trades and one unsequenced rejection report, and change neither original book nor counters. Exceptions, including allocation failure while cloning, filling, resting the remainder or constructing output, propagate with the original state untouched. The only operations following the swap are nonthrowing assignments and return of movable standard vectors. No partially produced executions are exposed. Maintenance methods use the same clone-and-swap boundary. A book aggregate overflow, counter exhaustion, stale selection or invalid fill rejects the whole submit. Allocation failure injection tests exercise the transaction, although they cannot prove every implementation-specific failure path.

This deliberately copies all resting orders for each accepted submission or maintenance operation. For `N` orders and `P` levels, cloning takes expected `O(N log P)` and `O(N + P)` space; matching `F` orders adds expected `O(F log P)` for level removals. This correctness-first design is not a latency claim; profiling and a carefully specified lower-cost transaction strategy are future work.

## Sequencing and results

Counters hold the last issued values, initially zero. Each successful submit or successful `cancel_resting` / `modify_resting` maintenance operation increments the command counter once. Rejected operations do not advance counters. Each trade receives the next trade ID and the next shared event sequence; accepted, fill and terminal reports also receive event sequences in emission order. A command with multiple trades consumes one trade ID per execution and emits resting and incoming fill reports after each trade. A limit remainder gets a resting report; a market remainder gets a cancellation report. The report identifies the participant and remaining quantity. Rejection is expressed by `Outcome.error`, zero command sequence, and one rejection report with sequence zero (not an accepted event). An optional initial `Counters` argument is a last-issued-value seed; callers must persist/restore it consistently with the book. Any exhausted counter rejects the whole command before commit. No wall clock participates.

`Request` accepts raw fields for explicit validation. `Outcome` contains a command sequence, remaining quantity, trades and typed reports. `find`, `depth` and `orders_at` return values. `cancel_resting` and `modify_resting` are book maintenance, not exchange-level cancel/replace commands: they increment the accepted command counter but do not emit reports or trades. Resting sequence metadata is the command sequence of the original insertion; list position, not that metadata, determines priority after a modification. Market remainder quantity is reported as cancelled, not resting. IDs can be reused after removal; generated trade IDs are unique only within an engine initialized with a coherent counter.

## Future replay and limitations

Replay must record ordered submissions and maintenance commands, input IDs and seed counters; identical streams and initial state produce identical outputs. Snapshotting and durable recovery are not implemented. There is no book import in this phase, so restoring nonzero counters alone does not restore state. Original order quantity and cumulative fills are not retained in resting snapshots after amendments. Fill events must later be coordinated atomically with durable logging and publication. Signed external quantities must be validated before conversion to unsigned values.
